# Storage Design

This document describes where Kokoro Reader stores data and why.

## Storage roots

The app uses two app-private storage roots:

```text
cache/kokoro_audio/
files/kokoro_history/
```

Android owns these directories. They are not shared with other apps, and they can be deleted by uninstalling the app or clearing app data.

## Transient audio cache

Generated or downloaded page audio is first written to:

```text
cache/kokoro_audio/page_0001_<hash>.mp3
```

The exact extension depends on the configured response format. The filename hash includes:

- server URL;
- model;
- voice/mix;
- TTS speed;
- response format;
- stream flag;
- language code;
- Kokoro normalization options;
- page index;
- page text.

This makes cache reuse safe when voice/settings/text differ.

The transient cache is allowed to be disposable. The Settings **Clear Audio Cache** action deletes only this cache. Saved history audio is not deleted by that action.

## History root

Generated speech sessions are stored under:

```text
files/kokoro_history/<session-id>/
```

The session id is a short SHA-256 prefix of:

- the normalized full text;
- the current TTS settings key.

This means the same text with the same voice/settings reuses the same history session, while a different voice/speed/model creates a different session.

## Session metadata

Each retained session stores:

```text
files/kokoro_history/<session-id>/session.json
```

The JSON contains:

- schema id/version by convention through documented fields;
- `id`;
- `createdAt`;
- `updatedAt`;
- `currentPage`;
- `pageCount`;
- `charCount`;
- title preview;
- normalized full text;
- TTS settings snapshot;
- count of saved audio files.

The full text is intentionally stored because the History screen must be able to reload a session without depending on SharedPreferences or the transient editor state.

## History audio

Saved history audio is stored below the session directory:

```text
files/kokoro_history/<session-id>/audio/page_0001_<hash>.mp3
```

This layout separates human-readable metadata from potentially large binary audio files.

The app also checks the older layout where audio was stored directly in the session directory. That fallback is kept so early history generated by development builds remains playable.

## Retention policy

The Settings field **History sessions to keep** controls retention:

- `20` is the default.
- Values are clamped between `0` and `200`.
- `0` disables history retention and prunes saved history.

Pruning sorts sessions by `updatedAt` descending and deletes sessions beyond the retention limit. The transient audio cache is not part of this retention policy.

## Offline behavior

Playback lookup order is:

1. Transient cache.
2. Saved history audio, if history retention is enabled.
3. Legacy history audio fallback, if present.
4. Kokoro server generation.

A session is fully offline-ready when every page has audio in cache or saved history.

## Why not store everything in SharedPreferences?

SharedPreferences is used only for small user preferences and last-session pointers. Session metadata and audio use files because:

- audio files are binary and large;
- JSON files are easier to inspect and migrate;
- pruning whole session directories is straightforward;
- the storage layout remains natural for future export/import features.
